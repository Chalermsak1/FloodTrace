# สถาปัตยกรรมความปลอดภัย การกู้คืนระบบ และคู่มือรับมือภัยคุกคาม (SECURITY & RUNBOOKS)
**ขอบเขตระบบ:** แพลตฟอร์ม FloodTrace จังหวัดปราจีนบุรี  
**สถานะการตรวจสอบ:** ร่างฉบับตรวจสอบเพื่อการใช้งานจริง (AUDIT READY)  
**วันที่ตรวจสอบล่าสุด:** 2026-10-02  

---

## 1. สถาปัตยกรรมความปลอดภัยของระบบ (Security Architecture)

ระบบ FloodTrace ได้รับการออกแบบตามหลักการ **"Defense-in-Depth (การป้องกันเป็นชั้นเชิง)"** และ **"Least Privilege (การให้สิทธิ์เท่าที่จำเป็น)"** โดยมีโครงสร้างการรักษาความปลอดภัยดังนี้:

```
[ ผู้ใช้งานทั่วไป / อินเทอร์เน็ต ]
              │
              ▼
    [ CDN / DDoS Shield ]          <-- ป้องกันการยิงถล่มคำขอ (Cloudflare / AWS Shield)
              │
              ▼
    [ WAF & Reverse Proxy ]        <-- กรองคำขออันตราย ตรวจสอบขนาด Body และตัด Rate Limit
              │
              ▼
    [ FastAPI Application Layer ]  <-- ตรวจสอบสิทธิ์ (RBAC), ถอดรหัส, และกำกับ X-Request-ID
              │
              ▼
    [ เครือข่ายส่วนตัวภายใน (VPC) ]  <-- ตัดการเชื่อมต่อจากโลกภายนอกโดยสมบูรณ์
              │
              ▼
    [ PostgreSQL + PostGIS ]       <-- ผูกไว้เฉพาะพอร์ตภายใน เข้ารหัสข้อมูล และจำกัด Statement Timeout
```

## 2. การแยกฐานข้อมูลและเครือข่ายภายใน (Database Network Isolation)

1. **ไม่เปิดพอร์ตสู่สาธารณะ:** ฐานข้อมูล PostgreSQL/PostGIS ผูกไว้เฉพาะในเครือข่ายเสมือนส่วนตัว (Internal Docker Network / VPC Subnet) ห้ามเปิดพอร์ต 5432 ออกสู่อินเทอร์เน็ตสาธารณะอย่างเด็ดขาด
2. **การบริหารจัดการ Connection Pool:**
   - `DB_POOL_SIZE = 10`: จำนวนการเชื่อมต่อพื้นฐานที่เปิดพร้อมใช้งาน
   - `DB_MAX_OVERFLOW = 20`: จำนวนการเชื่อมต่อสูงสุดที่ยอมให้ขยายได้ชั่วคราวขณะมีทราฟฟิกสูง
   - `DB_POOL_TIMEOUT = 30 วินาที`: หากไม่มี Connection ว่างภายใน 30 วินาที จะตัดการทำงานพร้อมส่งข้อความแจ้งเตือนอย่างปลอดภัย
   - `DB_STATEMENT_TIMEOUT = 10,000 มิลลิวินาที (10 วินาที)`: ตัดคำสั่ง SQL ที่ใช้เวลาประมวลผลนานผิดปกติ เพื่อป้องกันการเกิด Database Exhaustion
3. **การตรวจสอบความมีชีวิตของฐานข้อมูล:** ใช้ระบบ `pool_pre_ping=True` ตรวจสอบคำสั่ง `SELECT 1` ก่อนส่งคิวรีจริงเสมอ หากการเชื่อมต่อหลุดจะทำการต่อใหม่โดยอัตโนมัติ

## 3. การยืนยันตัวตนและบทบาทหน้าที่ (Authentication & RBAC)

ระบบแบ่งระดับผู้ใช้งานออกเป็น 4 บทบาทหลักตามหลัก Least Privilege:

| บทบาท (Role) | สิทธิ์การเข้าถึง | การยืนยันตัวตน | ความรับผิดชอบ |
|---|---|---|---|
| **`PUBLIC`** (ประชาชนทั่วไป) | ดูแผนที่ ค้นหาพื้นที่ ส่งรายงานเหตุการณ์ ดูผลตรวจทางการ | ไม่ต้องมีบัญชีผู้ใช้งาน เพื่อความสะดวกและไม่สร้างอุปสรรคต่อการรับรู้ภัย | อ่านข้อมูลสาธารณะและส่งรายงานเบาะแส |
| **`REPORTER`** (อาสาสมัครในพื้นที่) | ส่งรายงานภาคสนามพร้อมแนบภาพถ่ายหลายรูป | ยืนยันผ่านเบอร์โทรศัพท์ (SMS OTP) หรือรหัสผ่านแบบใช้ครั้งเดียว | รายงานข้อสังเกตที่มีความถี่สูง |
| **`REVIEWER`** (เจ้าหน้าที่ตรวจประเมิน) | ตรวจสอบรายงานของประชาชน ปรับสถานะเป็นทางการ | บัญชีเจ้าหน้าที่ + การยืนยันตัวตนแบบหลายปัจจัย (MFA) | กลั่นกรองข้อมูลและประสานงานห้องแล็บ |
| **`ADMIN`** (ผู้ดูแลระบบความปลอดภัย) | จัดการระบบ ตรวจสอบ Log กู้คืนฐานข้อมูล ตั้งค่า API | กุญแจลับเฉพาะ (`ADMIN_API_KEY`) + IP Whitelist + MFA | ดูแลเสถียรภาพและความปลอดภัยของแพลตฟอร์ม |

## 4. การป้องกันการเรียกใช้ API และความปลอดภัยของส่วนหัว (API Hardening)

1. **การจำกัดอัตราการเรียกใช้ (Rate Limiting):**
   - การเปิดดูข้อมูลทั่วไป: สูงสุด **60 คำขอ/นาที** ต่อหนึ่ง IP Address
   - การส่งรายงานข้อสังเกต: สูงสุด **10 คำขอ/นาที** เพื่อป้องกันสแปม
   - การเข้าสู่ระบบผู้ดูแล: สูงสุด **5 คำขอ/นาที** เพื่อป้องกัน Brute-force
   - เมื่อเกินกำหนด ระบบจะตอบกลับด้วยรหัส **429 (Too Many Requests)** พร้อมเวลาที่สามารถลองใหม่ได้
2. **ส่วนหัวความปลอดภัย (Security Headers):**
   - `Strict-Transport-Security (HSTS)`: บังคับใช้ HTTPS ตลอดเวลา (`max-age=31536000; includeSubDomains`)
   - `Content-Security-Policy (CSP)`: จำกัดแหล่งที่มาของสคริปต์ ป้องกันการโจมตีแบบ XSS
   - `X-Frame-Options: DENY`: ป้องกันการฝังเว็บไซต์ใน iframe (Clickjacking)
   - `X-Content-Type-Options: nosniff`: ป้องกัน MIME-type Sniffing
   - `X-Request-ID`: สร้างรหัสประจำคำขอแบบ UUIDv4 ทุกครั้ง เพื่อใช้แกะรอยประวัติใน Log
3. **การป้องกันคำขอซ้ำซ้อน (Idempotency Key):**
   - การส่งรายงานเหตุการณ์รองรับ `X-Idempotency-Key` เพื่อป้องกันไม่ให้เกิดรายงานซ้ำในกรณีที่ผู้ใช้กดยืนยันหลายครั้งขณะเน็ตช้า

## 5. กระบวนการอัปโหลดรูปภาพอย่างปลอดภัย (Secure Photo Upload Pipeline)

เพื่อป้องกันการอัปโหลดไฟล์ไม่พึงประสงค์ (Web Shell / ไวรัส) ระบบมีขั้นตอนการกรอง 6 ขั้นตอน:
1. **ตรวจสอบ Magic Bytes:** ตรวจสอบส่วนหัวของไฟล์จริง ต้องเป็น `image/jpeg` หรือ `image/png` เท่านั้น ไม่เชื่อส่วนขยายไฟล์ที่ส่งมา
2. **จำกัดขนาดไฟล์:** กำหนดขนาดสูงสุดไม่เกิน **5 MB**
3. **การถอดรหัสอย่างปลอดภัย (Safe Decoding):** โหลดภาพเข้าหน่วยความจำผ่านไลบรารี Pillow เพื่อยืนยันว่าเป็นไฟล์ภาพที่สมบูรณ์
4. **การลบข้อมูลพิกัดและกล้อง (EXIF Stripping):** ลบข้อมูลส่วนตัว วันเวลาถ่าย พิกัด GPS และยี่ห้อกล้องทั้งหมดออกจาก Metadata
5. **การแปลงรหัสใหม่ (Re-encoding):** ทำการ Re-encode บันทึกภาพใหม่เป็นภาพบริสุทธิ์เพื่อกำจัด Payload ที่อาจซ่อนอยู่ในพิกเซล
6. **การสุ่มชื่อไฟล์:** ตั้งชื่อไฟล์ใหม่ด้วย UUIDv4 แบบสุ่ม (เช่น `img_a8b9c...jpg`) และจัดเก็บในไดเรกทอรีที่ไม่อนุญาตให้รันสคริปต์ (No-Execution Flag)

## 6. การสำรองข้อมูลและการซ้อมกู้คืนระบบ (Database Backup & Disaster Recovery)

### แผนการสำรองข้อมูล (Backup Strategy)
- **ความถี่ในการสำรองข้อมูล:** อัตโนมัติทุก 6 ชั่วโมง (หรือทุกวันในสภาวะปกติ)
- **เป้าหมาย RPO (Recovery Point Objective):** $\le 1$ ชั่วโมง (ข้อมูลจะสูญหายย้อนหลังไม่เกิน 1 ชม.)
- **เป้าหมาย RTO (Recovery Time Objective):** $\le 30$ นาที (ระบบต้องฟื้นกลับมาให้บริการได้ภายใน 30 นาที)
- **การจัดเก็บ:** ไฟล์สำรองถูกบีบอัดเป็น `.sql.gz` เข้ารหัส และจัดเก็บแยกคนละโหนดกับเซิร์ฟเวอร์หลัก

### สรุปผลการซ้อมกู้คืนระบบ (Drill Verification Result)
- ดำเนินการทดสอบผ่านสคริปต์: `scripts/backup_restore_drill.py`
- เวลาที่ใช้ในการสำรองข้อมูล: **0.13 วินาที**
- เวลาที่ใช้ในการกู้คืนเข้าสู่ฐานข้อมูลทดสอบ: **0.94 วินาที**
- ผลการตรวจความสมบูรณ์: โครงสร้างตาราง (Schema) ครบถ้วน, ข้อมูลเรขาคณิต PostGIS สมบูรณ์ 100%, ระบบทำงานต่อได้ทันที

## 7. คู่มือการปฏิบัติการเมื่อเกิดเหตุขัดข้อง (Incident Response Runbooks)

### Runbook 1: ระบบ API ขัดข้อง ไม่ตอบสนอง (API Outage)
- **อาการ:** ระบบแสดงข้อผิดพลาด `502 Bad Gateway` หรือ `504 Gateway Timeout` หน้าเว็บหมุนค้าง
- **ตรวจอะไร:** 
  1. ตรวจสอบสถานะ Process: `sudo systemctl status floodtrace-api` หรือ `docker ps`
  2. ตรวจสอบ CPU/Memory: คำสั่ง `top` หรือ `htop` ว่ามีการใช้ทรัพยากรเต็ม 100% หรือไม่
  3. ตรวจสอบ Log ล่าสุด: `tail -n 100 logs/floodtrace.log` เพื่อดูว่าเกิด Unhandled Exception ใด
- **ทำอย่างไร:** 
  1. หาก Process ดับ ให้สั่งเริ่มใหม่: `sudo systemctl restart floodtrace-api`
  2. หากหน่วยความจำเต็ม ให้ตรวจสอบว่ามี Request ใดประมวลผล GIS หนักเกินไปแล้วทำการ Kill Process
- **คาดหวังอะไร:** Endpoint `/health/live` ต้องตอบกลับ `{"status": "alive"}` ภายใน 5 วินาที
- **เมื่อไรควร Escalate:** หาก Restart แล้วยังค้างเกิน 5 นาที หรือเกิดการ Crash ซ้ำซาก ให้แจ้ง Lead Backend Engineer

### Runbook 2: ฐานข้อมูล PostgreSQL ขัดข้อง (Database Outage)
- **อาการ:** Endpoint `/health/ready` ตอบกลับ HTTP 503, Log แสดงข้อความ `OperationalError: could not connect to server`
- **ตรวจอะไร:**
  1. ตรวจสอบสถานะเซิร์ฟเวอร์ฐานข้อมูล: `sudo systemctl status postgresql`
  2. ตรวจสอบพื้นที่ว่างบนดิสก์: คำสั่ง `df -h`
  3. ตรวจสอบจำนวน Connection ที่ค้าง: คิวรีดู `pg_stat_activity`
- **ทำอย่างไร:**
  1. หากดิสก์เต็ม ให้ลบไฟล์ Temp หรือขยายพื้นที่จัดเก็บทันที
  2. หาก Connection เต็ม ให้ Restart บริการและตรวจสอบว่าแอปพลิเคชันคืน Connection เข้า Pool ครบหรือไม่
- **คาดหวังอะไร:** `/health/ready` ตอบกลับสถานะ `database: HEALTHY` ภายใน 10 วินาที
- **เมื่อไรควร Escalate:** หากพบว่าไฟล์ระบบของ PostgreSQL เสียหาย ให้เริ่มขั้นตอน Disaster Recovery กู้คืนจาก Backup ล่าสุด

### Runbook 3: แหล่งข้อมูลภายนอกล่มหรือช้าผิดปกติ (Source Outage / Degradation)
- **อาการ:** หน้าแดชบอร์ดมีข้อความแจ้งเตือน "ข้อมูลระดับน้ำยังไม่พร้อมใช้งาน" หรือ "แหล่งข้อมูลปิดกั้นชั่วคราว"
- **ตรวจอะไร:** ตรวจสอบสถานะ Circuit Breaker ผ่าน `/health/sources` ดูว่าแหล่งใดขึ้นสถานะ `OPEN`
- **ทำอย่างไร:** ไม่ต้องดำเนินการแก้ไขที่โค้ด ระบบ Circuit Breaker จะทำการตัดการเชื่อมต่ออัตโนมัติเพื่อไม่ให้ระบบค้าง และจะทดลองส่งคำขอใหม่ (HALF_OPEN) เมื่อพ้นระยะ Cooldown
- **คาดหวังอะไร:** หน้าเว็บต้องแสดงคำเตือนอย่างสง่างาม (Graceful Degradation) ฟังก์ชันอื่นยังต้องใช้งานได้ปกติ
- **เมื่อไรควร Escalate:** หากแหล่งข้อมูลหลักปิดปรับปรุงนานเกิน 24 ชั่วโมง ให้ประสานงานหน่วยงานเจ้าของข้อมูล

### Runbook 4: ข้อมูลผิดปกติหรือเกิดการเสียหาย (Data Corruption Detected)
- **อาการ:** มีรายงานหรือพิกัดที่อยู่นอกเขตจังหวัดปราจีนบุรี หรือค่าระดับน้ำติดลบผิดปกติ
- **ตรวจอะไร:** ตรวจสอบพิกัดในตาราง `citizen_reports` และ `water_stations` ผ่านฟังก์ชัน `ST_Within()`
- **ทำอย่างไร:** กักกันระเบียนที่มีปัญหาด้วยคำสั่ง SQL ปรับสถานะเป็น `CORRUPTED` เพื่อไม่ให้ถูกนำไปแสดงผลบนแผนที่
- **คาดหวังอะไร:** แผนที่แสดงผลเฉพาะข้อมูลที่ถูกต้องตามหลักภูมิศาสตร์เท่านั้น
- **เมื่อไรควร Escalate:** หากพบว่ามีการแก้ไขข้อมูลจากบุคคลภายนอก ให้เข้าสู่ขั้นตอนตรวจสอบการบุกรุก

### Runbook 5: กุญแจลับรั่วไหล (Credential Leakage)
- **อาการ:** ตรวจพบ `ADMIN_API_KEY` หรือ Database Password ปรากฏใน Git Repository หรือ Log สาธารณะ
- **ตรวจอะไร:** ตรวจสอบประวัติ Git Commit และ Server Log ล่าสุด
- **ทำอย่างไร:** 
  1. เพิกถอนและสร้าง Secret ใหม่ทันที
  2. อัปเดตไฟล์สภาพแวดล้อม `.env` บนเซิร์ฟเวอร์
  3. Restart บริการทั้งหมดเพื่อโหลดกุญแจใหม่
- **คาดหวังอะไร:** กุญแจเดิมต้องถูกปฏิเสธด้วยรหัส 401 Unauthorized ทันที
- **เมื่อไรควร Escalate:** แจ้ง Security Officer ทันทีเพื่อตรวจเช็กย้อนหลังว่ามีข้อมูลถูกดึงออกไปหรือไม่

### Runbook 6: การโจมตีแบบปฏิเสธการให้บริการ (DDoS Attack)
- **อาการ:** ทราฟฟิกพุ่งสูงผิดปกติ อัตราการตอบกลับช้าลงทั่วทั้งระบบ
- **ตรวจอะไร:** ดูสถิติคำขอใน Nginx Access Log ว่ามาจาก IP หรือ Subnet ใดซ้ำๆ
- **ทำอย่างไร:** 
  1. เปิดใช้งานโหมด "Under Attack" บน Cloudflare / CDN
  2. บล็อก IP กลุ่มเสี่ยงที่ระดับไฟร์วอลล์ (iptables / UFW)
  3. ปรับลด Rate Limit ชั่วคราว
- **คาดหวังอะไร:** ทราฟฟิกขยะถูกทิ้งที่ขอบระบบ (Edge) และผู้ใช้จริงสามารถใช้งานได้ตามปกติ
- **เมื่อไรควร Escalate:** หากปริมาณทราฟฟิกเกินกว่าแบนด์วิธของเซิร์ฟเวอร์ ให้ย้ายทราฟฟิกเข้า CDN Scrubbing Center

### Runbook 7: การอัปโหลดไฟล์อันตราย (Malicious File Upload)
- **อาการ:** ระบบความปลอดภัยของเซิร์ฟเวอร์ตรวจพบไฟล์สคริปต์ในไดเรกทอรีอัปโหลด
- **ตรวจอะไร:** ตรวจสอบโฟลเดอร์เก็บไฟล์ภาพ `storage/photos/`
- **ทำอย่างไร:** ลบไฟล์ดังกล่าวทันที และตรวจสอบว่า Magic-byte Validator และ Pillow Re-encoder ทำงานถูกต้องหรือไม่
- **คาดหวังอะไร:** ไฟล์ที่ไม่ใช่ภาพที่ถูกต้องจะถูกปฏิเสธตั้งแต่ขั้นตอนแรก
- **เมื่อไรควร Escalate:** หากไฟล์สามารถรันโค้ดได้ ให้ระงับฟังก์ชันอัปโหลดชั่วคราวและตรวจสอบช่องโหว่

### Runbook 8: การรั่วไหลของข้อมูลส่วนบุคคล (Privacy Breach)
- **อาการ:** มีผู้พบเห็นพิกัดบ้านพักอาศัยที่แม่นยำ หรือข้อมูลระบุตัวตนของผู้รายงานปรากฏบนแผนที่สาธารณะ
- **ตรวจอะไร:** ตรวจสอบฟิลด์ใน Public API `/api/v1/reports/` ว่ามีข้อมูลดิบหลุดรอดหรือไม่
- **ทำอย่างไร:** ปรับปรุงคิวรีให้ส่งออกเฉพาะพิกัดที่เบลอแล้ว (`latitude_blurred`, `longitude_blurred`) และล้างแคชฝั่งหน้าบ้าน
- **คาดหวังอะไร:** พิกัดบนแผนที่ต้องแสดงเฉพาะระดับตำบลหรือเบลอระยะ ~1.1 กม. เสมอ
- **เมื่อไรควร Escalate:** รายงานต่อเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO) ภายใน 72 ชั่วโมงตามกฎหมาย PDPA

### Runbook 9: การเผยแพร่ข้อมูลผิดพลาดโดยไม่ได้ตั้งใจ (Wrong Publication)
- **อาการ:** มีการเผยแพร่ข้อความที่ระบุว่าโรงงานแห่งหนึ่งปล่อยสารพิษ ทั้งที่ยังไม่มีผลตรวจแล็บรับรอง
- **ตรวจอะไร:** ตรวจสอบบัตรข้อมูลพื้นที่ (Area Card) หรือประกาศแจ้งเตือนล่าสุด
- **ทำอย่างไร:** ใช้ฟังก์ชัน **ระงับการเผยแพร่ทันที (Emergency Takedown)** โดยปรับสถานะเป็น `RETRACTED` และแสดงข้อความชี้แจงแก้ไข
- **คาดหวังอะไร:** ข้อมูลที่ผิดพลาดต้องหายไปจากหน้าจอผู้ใช้ทุกคนภายใน 1 นาที
- **เมื่อไรควร Escalate:** ประสานงานฝ่ายสื่อสารองค์กรและฝ่ายกฎหมายทันทีเพื่อออกแถลงการณ์แก้ไขข้อเท็จจริง

### Runbook 10: แบบจำลองพยากรณ์อากาศคาดการณ์คลาดเคลื่อนอย่างรุนแรง (Incorrect Forecast)
- **อาการ:** โมเดลแสดงว่าฝนตกหนักมาก แต่วัดจริงไม่มีฝน หรือข้อมูลดาวเทียมไม่อัปเดต
- **ตรวจอะไร:** เปรียบเทียบค่าพยากรณ์กับเรดาร์ตรวจอากาศจริงของกรมอุตุนิยมวิทยา
- **ทำอย่างไร:** ปรับสวิตช์ Feature Flag ปิดการแสดงผลเลเยอร์พยากรณ์ชั่วคราว และแสดงป้ายกำกับ "อยู่ระหว่างปรับปรุงแบบจำลอง"
- **คาดหวังอะไร:** ผู้ใช้ไม่เกิดความตื่นตระหนกจากข้อมูลคาดการณ์ที่คลาดเคลื่อน
- **เมื่อไรควร Escalate:** รายงานไปยังนักอุตุนิยมวิทยาของโครงการเพื่อปรับค่า Calibration Factor

### Runbook 11: ชั้นข้อมูลแผนที่แสดงผลผิดพลาด (Incorrect Map Layer)
- **อาการ:** แนวแม่น้ำหรือขอบเขตอำเภอบิดเบี้ยว หรือซ้อนทับผิดตำแหน่ง
- **ตรวจอะไร:** ตรวจสอบ Coordinate Reference System (CRS) ของไฟล์ GeoJSON ต้องเป็น `EPSG:4326 (WGS84)`
- **ทำอย่างไร:** ทำการ Re-project ข้อมูลเวกเตอร์ให้ถูกต้อง และล้าง Browser Cache
- **คาดหวังอะไร:** ขอบเขตภูมิศาสตร์ทับซ้อนกับภาพถ่ายดาวเทียมอย่างแม่นยำ
- **เมื่อไรควร Escalate:** ส่งไฟล์ให้ GIS Specialist ดำเนินการตรวจสอบ Topological Integrity

### Runbook 12: ระบบแจ้งเตือนล้มเหลว (Notification Dispatch Failure)
- **อาการ:** มีเหตุฉุกเฉินแต่นาฬิกาหรือระบบแจ้งเตือนไม่ส่งข้อมูลหาประชาชน
- **ตรวจอะไร:** ตรวจสอบคิวงานเบื้องหลัง (Background Worker / Redis Queue)
- **ทำอย่างไร:** สั่งประมวลผลงานที่ค้างในคิวใหม่ (Retry Dead-letter Queue) และตรวจสอบโควตา API ของบริการส่งข้อความ
- **คาดหวังอะไร:** ประชาชนในพื้นที่เสี่ยงได้รับข้อความแจ้งเตือนย้อนหลังครบถ้วน
- **เมื่อไรควร Escalate:** หากเป็นเหตุการณ์น้ำหลากวิกฤต ให้ประสานงานผ่านช่องทางวิทยุกระจายเสียงท้องถิ่นควบคู่
